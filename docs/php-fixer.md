# php-fixer: How the Hook Runs DressCode

The `php-fixer` plugin runs [DressCode](https://github.com/dg/dresscode) (`dresscode/dresscode`, source in `W:\libs\Dress-Code` on the maintainer's machine) after every Claude Code `Edit`/`Write` and Codex `apply_patch` of a `.php` or `.phpt` file. The hook is `plugins/php-fixer/hooks/fix-php-style.php`, its tests `tests/fix-php-style*.phpt`. Version 2.0.0 replaced the 1.x plugin, which ran `ecs` of nette/coding-standard 3, and keeps that one running for users who have not migrated yet (see Migration from 1.x).

This page records how the hook works and why, so that a change keeps the decisions below or changes them knowingly. The DressCode side keeps its own note on this consumer in `docs/local/findings/php-fixer-hook.md` of its repository; keep the two in step.


## Decisions

**DressCode is configured by `dresscode.neon` alone.** Which standard, sets, decisions, exclusions, target PHP version and baseline apply is the business of the project's DressCode configuration, the same one its CI runs. The hook reads nothing from `.nette-claude.json`, in the 1.x fallback neither, not even when a project still has a `fix-php-style` section there and no `dresscode.neon`: such a project gets the Nette standard and its old exclusions no longer apply. A second place for the same knowledge would only drift from the first, and the section was added shortly before 2.0.0, so nobody is believed to use it. Nothing converts it, and the migration does not mention it. `.nette-claude.json` remains for the lint hooks of `nette-lint`.

**Without a configuration, the Nette coding standard.** DressCode itself refuses to run without a configuration or a preset, so the hook adds `--use nette` exactly when it found no configuration file, never otherwise: a project with a configuration gets no standard laid over it.

**A project-local DressCode and a global one are both supported, the local one wins.** The hook takes `vendor/bin/dresscode` found upwards from the edited file (`findUpwards()`, which stops one level above the `.git` root), otherwise `vendor/bin/dresscode` in the global Composer home (`composer global require dresscode/dresscode`: `COMPOSER_HOME`, on Windows `%APPDATA%/Composer`, elsewhere the XDG or `~/.composer` directory). PATH is never consulted. Either must be DressCode 1.3 or newer, the first with the format `agent`, `--lines` and `--before`. The local copy wins because only its autoloader knows the extensions (rule packages) its configuration names. The skills install globally by default and into the project when it has PHPStan. `typeAnalysis: phpstan` takes the types from the `phpstan/phpstan` of the DressCode process, so a global DressCode gets a global PHPStan beside it, and every `dresscode.neon` the skills write has `typeAnalysis: phpstan`. A global PHPStan reads the classes of the project and of its `vendor` statically and runs none of its code, so it sees them although the global process does not have the project's autoloader; tested with the decisions `upgrading.declarations.deprecatedMember` and `upgrading.declarations.deprecatedClass`. For a project with PHPStan of its own the skills recommend DressCode in the project, so that the PHPStan of the project, its version and its extensions apply; a global DressCode over a project whose `phpstan.neon` includes extensions from its `vendor` would likely not find their classes (not verified). The types cost: one run over one file took about 410 ms with them and 150 ms without (a rough measurement). When neither DressCode nor the old `ecs` exists, the hook exits 0 silently: the plugin is optional and the `install-php-fixer` skill installs DressCode.

**The fixer never rewrites a file silently.** Claude must learn every rewrite, or its next `Edit` built on the old content fails or, worse, reintroduces what the fixer removed (an unused `use`). Every rewrite is reported, also when DressCode left violations as well.

**DressCode owns the text, the hook owns the envelope.** What Claude reads about the file (the diff of the rewrite, the imports removed, what is left and what to do about it) is written by DressCode's format `agent`, which alone knows it. The hook passes it on without rewording, filtering or looking for markers in it, and wraps it the way the client wants it. It has words of its own only where DressCode did not run: no binary, a process that would not start, a timeout, the migration notice of 1.x. A hook that edited the text would decide what the agent hears in code untested against a format that changes in another repository.


## How a Run Goes

1. The file must have the `.php`/`.phpt` extension and exist.
2. The configuration is searched the way DressCode's `Config\Loader::find()` does: upwards **to the filesystem root**, not just to `.git`, for `dresscode.neon`, `dresscode.php` and both `.dist` variants. The hook only needs the directory; which file wins and the conflict of two formats are left to DressCode. Without one the nearest `composer.json` (`findUpwards()`) marks the project, and a file with neither belongs to no PHP project and is left as written, with exit 0 also in the 1.x way: typically a scratch script of the agent in the temporary directory, where the Nette standard would only make noise. A `.git` alone does not make a project, because a home directory kept in Git (the maintainer's is) would make one of every stray file under it.
3. The binary is chosen as described above; without DressCode the run goes the 1.x way (see Migration from 1.x), without that too it ends with exit 0.
4. `php -l` guard: a file with a syntax error is skipped silently. `lint-php` of `nette-lint` reports it, and hooks run in parallel in no fixed order, so the fixer cannot rely on it having run.
5. The working directory is the configuration's directory, without one that of the `composer.json`. DressCode searches for its configuration from the working directory and takes it as the root when there is none, so the hook changes into the right directory and passes the **absolute** path of the file.
6. The command: `PHP_BINARY -c <the hook's php.ini> <bin> fix <file> --format agent --no-color --skip-excluded --set mistakes.debugOutput=keep [--fix-risky=file.strictTypes.declaration] [--use nette] [--lines <range>...] [--before <file>]`, with `-n` instead of `-c` when the hook itself runs without an ini. The same PHP and ini as the hook, because the bare binary would load the default `php.ini` (on the maintainer's machine one with Xdebug). It is started by `proc_open()` with an argument list, so no shell quotes anything, and stdout and stderr go to two temporary files, read apart.
   - `--format agent`: the whole message for the model on stdout. A clean file prints nothing; a rewritten one "DressCode changed `<path>`; the changes below are already in the file:" with the removed imports named and the hunks in a fenced `diff` (over a budget a summary telling the agent to read the file); what is left follows under "Left in `<path>`, at the lines of the file as it is now:", each violation with what to do about it. Warnings of the configuration (a decision the target PHP is too old for) are left out, the agent having nothing to do with them. Stderr carries only what arises outside the report, a mistake of the command line or of the configuration.
   - `--skip-excluded`: a file named on the command line still passes through `excludePaths`; without it the hook would rewrite `fixtures*` the project excludes. DressCode's default exclusions (`vendor`, `node_modules`, `temp`, `tmp`, `log`, `.*`) apply even without a configuration, so a file under `.github/` or `.claude/` is never formatted.
   - `mistakes.debugOutput=keep`: the decision, where a configuration forbids it (the set `correctness` does), comments out `dump()`, `var_dump()` and their kin, which would destroy debugging calls in the middle of work. `--set` lays the value over the configuration of the project for this run only.
   - `--fix-risky=file.strictTypes.declaration`: only for a file Claude Code has just created (`tool_response.type` is `create`), which has no past behaviour the declaration would change, so a standard requiring `strict_types` adds it instead of leaving it to the agent. The consent turns nothing on, a standard without the requirement stays as it is. Otherwise the consent to risky fixes is the project's `fixRisky` alone. Codex sends no such type, so its new files are left to the agent.
7. The result by DressCode's exit code (`0` clean or fixed, `1` a violation of severity error or a syntax error left, `2` a file failed, `3` a mistake of the command line or of the configuration):
   - `0`: exit 0; when stdout says something, JSON on stdout with `hookSpecificOutput.additionalContext` holding it, encoded with `JSON_INVALID_UTF8_SUBSTITUTE` so that a stray byte of the file does not lose the message.
   - anything else: exit 2 with stdout on stderr, which the client shows Claude as an error; when stdout is empty, DressCode's stderr instead, and when both are, a sentence naming the exit code.
   - DressCode not finished in 50 s: the process is stopped and the hook fails with a sentence telling Claude to read the file again; one that could not be started fails with a sentence of its own.

One run takes roughly 200-250 ms.

**The file keeps its own style, and the edit is fixed wherever it reaches.** The hook passes the file as it was before the edit (`tool_response.originalFile`, written to a temporary file) as `--before`, and DressCode leaves every decision that text already broke as the file writes it, so an edit of a file not yet up to the dress code rewrites nothing far from it and a file indented by spaces stays so; every decision the file kept is fixed in the whole file, because a violation of it is one the edit made wherever it stands, an import whose last use it removed or the lines it put into a new block. The agent is told which decisions the file does not follow, to write in its style there.

**What is left is listed for the lines the edit wrote.** The hook passes them as `--lines` (`findEditedLines()`), and DressCode lists what stands on them and only counts the rest; with `--before` that holds for the decisions the file broke, while what the edit broke of the others is listed wherever it is. The range comes only from a source that proves it: the hunks Claude Code sends as `tool_response.structuredPatch` with `Edit` and with a `Write` of an existing file, numbered in the file as the edit left it, or the hunks of a Codex patch, each placed where its lines after the edit stand exactly once in the file. A line a hunk adds is in the range, and where a run of changes only took lines away, the line now standing in their place. A `Write` of a new file (`structuredPatch: []`), a hunk of another shape and a Codex hunk found nowhere or twice give no range, and DressCode then lists everything. The range never comes from searching `new_string` in the file, which picks an older occurrence of the same text above the edit and has nothing to search after `replace_all` or a deletion. `runHookFiles()` hands each child process of a multi-file Codex patch its file as a one-file patch (`tool_input.command` holding the sections that edited it, beside `file_path` and the event's `cwd`), the same input a one-file patch gives the hook directly.


## Migration from 1.x

Users of 1.x have `nette/coding-standard` installed globally and no DressCode. An upgrade of the plugin must not take their formatting away silently, so until DressCode is installed the hook keeps working as 1.x did and offers the migration:

- **Only the global `ecs` exists, the project has no DressCode configuration:** `fixWithCodingStandard()` runs `ecs fix <file> --config-file hooks/ncs.php` as 1.x did, only without its exclusions in `.nette-claude.json` (see above). `ecs` is run directly, without PHP in front; on Windows cmd finds `ecs.bat` by PATHEXT.
- **Only the global `ecs` exists, the project has a DressCode configuration:** nothing is formatted, because `nette/coding-standard` would fight the project's own configuration. The notice is given.
- **The notice** (`noticeMigration()`) tells Claude that the plugin now formats with DressCode, which is not installed, and to offer the `migrate-to-dresscode` skill with the user's consent. It goes along with the result, as `additionalContext` or on stderr with an error. It is given once a session: a marker file `nette-php-fixer-<md5 of session_id>` in the system temp directory, and then it says so ("This notice comes once a session."), because without that sentence an agent told the user the notice would come after every edit. A client that sends no `session_id` gets it every time, without the sentence. For a Codex patch with several files `runHookFiles()` hands the `session_id` to each child process.

The `migrate-to-dresscode` skill, which Claude may run on its own once the user agrees (unlike `install-php-fixer`, a manual one for a fresh installation), installs DressCode into the project when it has PHPStan and globally with PHPStan otherwise, writes `dresscode.neon` by hand (`use: nette`, `paths`, `fileExtensions` for `.phpt` tests, `typeAnalysis: phpstan`), keeps an existing configuration, shows the impact with `dresscode check` without fixing the project, and finally offers to remove the global `nette/coding-standard`. `paths` is required: without it `dresscode check` ends with "No paths given and none configured". A risky fix is made only with the user's consent for one decision (`--fix-risky=<path>`); `fix --ask-risky` needs an interactive terminal the agent does not have. `install-php-fixer` writes the same `dresscode.neon` for the current project when the user agrees, so both ways end in the same state.

The global `nette/coding-standard` 3.5 requires `nette/command-line ^1.9.2`, which conflicts with DressCode, so a global `composer require` of DressCode beside it fails (seen in the agent test). A new release of `nette/coding-standard` that allows `nette/command-line` 2 removes the conflict, but the version locked in the user's global installation must be updated first: `require` updates only the new package and its dependencies. The skill therefore runs `composer global update nette/coding-standard` before the installation, only when `composer global show nette/coding-standard` finds it: over a global Composer without `composer.json` the update fails with exit 1, over one without the package it does nothing. Until that release is out, the agent meets the conflict and offers to remove `nette/coding-standard` first.

## The `dresscode` Skill

The hook covers the file just edited; the `dresscode` skill covers DressCode run on purpose: `check` and `fix` over more files, the configuration, risky fixes, suppressions, the baseline, CI, and upgrades to newer PHP and library versions. It lives in this plugin because the plugin is what brings DressCode to an agent, and its description says it is not needed for ordinary edits, so it does not load beside `php-auto-fixer` at every PHP edit.

It bundles no manual. The manual of DressCode is written in Czech and follows the tool's own versions, so the skill teaches the model to ask the installed tool (`explain`, `config`, `catalogue`, `--help`), which answers for exactly that version and that project, and keeps only what the tool cannot say about itself: the model of decisions, standards, sets and target versions, the pitfalls of the configuration, and what the model must not decide alone (a fix over the whole project, risky fixes, suppressing, the baseline, `require.php`, installing packages). The longer material is in its `references/`: `configuration.md` and `upgrading.md`.

Unlike the hook, the skill names DressCode's commands, switches, configuration keys, decisions, presets and messages; after a change of any of those, check it as well.


## What the Hook Relies On in DressCode

Check these after every change of DressCode's command line; `tests/fix-php-style.phpt` runs the real global DressCode and catches most of them. All of them are in DressCode 1.3, the lowest version the hook supports:

- the `fix` command, the options `--format agent`, `--no-color`, `--skip-excluded`, `--set path=value`, `--use`, `--lines` (repeatable, `20` or `20-21` in the lines of the file as the edit left it, one past the end standing for the last), `--before <file>` (one file, the format `agent` only) and `--fix-risky=<decision>`
- the exit codes, and the streams of the format `agent`: the whole message on stdout, nothing for a clean file, stderr only for what arises outside the report
- the decision `mistakes.debugOutput` with its value `keep`, and the preset name `nette` (the configuration names decisions; the rule names of earlier DressCode versions are unknown now)
- the configuration file names and the upward search of `Config\Loader`
- `bin` in DressCode's `composer.json`, without which `composer global require` creates no binary


## Testing

`php vendor/bin/tester tests -s`. The tests of real runs need a DressCode and are skipped without it (`Environment::skip`): the binary the environment variable `DRESSCODE_BIN` names, otherwise the global one. The test hands it to the hook as the global one, through a Composer home of its own. The global copy is installed from GitHub, not from the local checkout, so a DressCode change not pushed yet is tested with `DRESSCODE_BIN=<checkout>/bin/dresscode php vendor/bin/tester tests -s`, and reaches the global copy only after it is pushed and `composer global update dresscode/dresscode phpsyntax/phpsyntax` runs. The global copy is usually a development version, so the lowest supported version is checked the same way, with `DRESSCODE_BIN` naming a copy of DressCode 1.3.0 installed by `composer install --no-dev`. `tests/fix-php-style-patch.phpt` uses a local stand-in for `vendor/bin/dresscode` and checks the plumbing (Codex patches, the working directory, the arguments, the streams and the envelope), not DressCode's rules. `tests/fix-php-style-legacy.phpt` covers the 1.x fallback with a stand-in for the global `ecs` (a `COMPOSER_HOME` of its own); the maintainer's global `nette/coding-standard` is a development version over DressCode, so the real version 3 cannot be checked on that machine.


## Known Consequences

- A repository without `dresscode.neon` is formatted by the Nette standard even when it follows other conventions. This repository has none either.
- `use` added in one edit and its first use in a later one: the fixer removes the import in between. The hook reports the rewrite, and the `php-auto-fixer` skill teaches the editing order.
- A PHP project with neither `composer.json` nor a DressCode configuration, a repository of loose scripts for instance, is not formatted; a `dresscode.neon` in its root turns the hook on.
